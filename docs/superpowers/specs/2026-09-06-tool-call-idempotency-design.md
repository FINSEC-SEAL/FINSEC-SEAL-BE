# Tool Call Idempotency Design

- Date: 2026-09-06
- Project: FINSEC-SEAL-BE
- Scope: State-changing sandbox Tool adapter idempotency
- Status: Approved design, pending implementation plan

## 1. Problem

Policy Gateway specification requires every state-changing adapter to provide unique idempotency on:

`(test_case_run_id, tool_call_id)`

Current runtime does not carry a canonical `tool_call_id` through the complete Tool execution path.

Current relevant contracts:

- `ToolProposal` contains only `toolName` and `arguments`.
- `SandboxExecutionContext` contains run/case/trace/mode/case context, but no tool-call identity.
- `ToolDispatcher` forwards `SandboxExecutionContext + ToolProposal` to `PolicyGateway`.
- `PolicyGateway` invokes the adapter after ALLOW.
- `ToolAdapter.execute(...)` receives only context and arguments.
- State-changing adapters currently include at least:
  - `LOAN_DECISION_UPDATE`
  - `EXTERNAL_HTTP` mock collector

Completed TestRun replay dedup already prevents a whole FA-05 run from executing twice, but that is a different boundary. It does not provide adapter-level exactly-once semantics when the same Tool invocation is retried inside an active run.

## 2. Design Goals

1. Spring owns canonical `tool_call_id`.
2. AI/provider identifiers are never authoritative.
3. Same `(test_case_run_id, tool_call_id)` executes a state-changing adapter at most once.
4. Same identity + same request returns the previously committed result.
5. Same identity + different request fails closed with `IDEMPOTENCY_CONFLICT`.
6. Adapter mutation, Tool execution evidence, and idempotency completion are atomic.
7. Read-only adapters do not pay the persistence cost of state-changing idempotency.
8. Existing FA-02/03/04/05 behavior remains compatible.
9. Flyway V1-V12 are never modified.
10. Real network access remains impossible for `EXTERNAL_HTTP`.

## 3. Canonical Tool Call Identity

Use the Spring-created `TOOL_PROPOSED` execution event ID as `toolCallId`.

```text
AI Tool Proposal
      |
      v
Spring validates proposal
      |
      v
TOOL_PROPOSED event
eventId = canonical toolCallId
      |
      v
AgentToolLoop
      |
      v
ToolDispatcher / PolicyGateway
      |
      v
State-changing adapter execution
```

Reasons:

- The identifier is generated by Spring, not the model.
- It is already durable execution evidence.
- It naturally belongs to one `test_case_run_id`.
- It supports deterministic replay correlation.
- It avoids introducing a second unrelated UUID for the same logical Tool call.

The associated `TOOL_PROPOSED.payload_digest` is the canonical request digest for replay validation.

## 4. Runtime Contract

Do not add `toolCallId` to `ToolProposal`.

`ToolProposal` remains model-originated semantic content:

```java
ToolProposal(
    String toolName,
    JsonNode arguments
)
```

Do not add `toolCallId` to `SandboxExecutionContext`.

That context remains run/case scope rather than invocation scope.

Introduce a Spring-owned invocation record:

```java
public record ToolInvocation(
        ToolProposal proposal,
        UUID toolCallId,
        String requestDigest
) {}
```

The invocation is created from the validated proposal plus its persisted `TOOL_PROPOSED` event.

### Initial proposal

`AgentRuntimeService.proposeTool(...)` already returns both:

- validated proposal
- `proposalEvent`

`AgentToolLoopService` constructs:

```text
ToolInvocation(
  proposal,
  proposalEvent.eventId(),
  proposalEvent.payloadDigest()
)
```

### Follow-up proposal

`recordFollowUpToolProposal(...)` must return the persisted proposal event together with the validated proposal, rather than returning only `ToolProposal`.

The next loop iteration therefore also receives a stable Spring-owned `toolCallId`.

## 5. Adapter Effect Classification

Extend `ToolAdapter` with a declarative effect:

```java
default ToolEffect effect() {
    return ToolEffect.READ_ONLY;
}

enum ToolEffect {
    READ_ONLY,
    STATE_CHANGING
}
```

Expected classification:

- `CUSTOMER_DATA_READ` -> `READ_ONLY`
- `EXTERNAL_HTTP` -> `STATE_CHANGING`
- `LOAN_DECISION_UPDATE` -> `STATE_CHANGING`

`stateChanged` in `ToolExecutionResult` remains runtime evidence about the actual execution result. `ToolEffect` is a static adapter capability declaration used before invocation.

A `STATE_CHANGING` adapter returning `stateChanged=false` is allowed for legitimate no-op semantics, but it is still executed through the idempotency boundary.

## 6. Database Schema

Create:

`V13__sandbox_tool_idempotency.sql`

No existing migration may be edited.

Create table:

```sql
sandbox_tool_idempotency_records
```

Required columns:

```text
id                    uuid primary key
test_case_run_id      uuid not null FK -> test_case_runs(id)
tool_call_id          uuid not null FK -> execution_events(id)
tool_name             varchar(100) not null
request_digest        sha256_digest not null
state                 varchar(20) not null
response_json         jsonb
state_changed         boolean
request_event_id      uuid FK -> execution_events(id)
response_event_id     uuid FK -> execution_events(id)
state_event_id        uuid FK -> execution_events(id)
completed_at          timestamptz
created_at            timestamptz not null default now()
```

State constraint:

```text
PROCESSING
COMPLETED
```

Uniqueness:

```sql
UNIQUE (test_case_run_id, tool_call_id)
```

Completion constraint:

- PROCESSING:
  - response_json null
  - state_changed null
  - response_event_id null
  - completed_at null
- COMPLETED:
  - response_json not null
  - state_changed not null
  - response_event_id not null
  - completed_at not null
- `state_event_id` is required only when `state_changed=true`.

Identity columns are immutable after insertion:

- test_case_run_id
- tool_call_id
- tool_name
- request_digest
- created_at

Only transition permitted:

```text
PROCESSING -> COMPLETED
```

## 7. Execution Service Boundary

Introduce one Spring service responsible for state-changing adapter idempotency:

```text
StateChangingToolExecutionService
```

Responsibilities:

1. Validate invocation identity.
2. Reserve `(caseRunId, toolCallId)`.
3. Detect duplicate calls.
4. Detect digest/tool mismatch.
5. Execute the adapter only for a new reservation.
6. Persist completion result and evidence references.
7. Reconstruct previous result for completed duplicate requests.

It does not evaluate security policy. Policy Gateway remains responsible for ALLOW/DENY.

It does not select adapters. Existing compile-time adapter registry remains authoritative.

## 8. Gateway Flow

### Read-only adapter

```text
POLICY_EVALUATED(ALLOW)
      |
      v
TOOL_REQUEST
      |
      v
adapter.execute(...)
      |
      v
TOOL_RESPONSE
```

### State-changing adapter

```text
POLICY_EVALUATED(ALLOW)
      |
      v
StateChangingToolExecutionService
      |
      +-- reserve idempotency identity
      |
      +-- TOOL_REQUEST
      |
      +-- adapter.execute(...)
      |
      +-- TOOL_RESPONSE
      |
      +-- SANDBOX_STATE_CHANGED when required
      |
      +-- mark receipt COMPLETED
```

The entire new-call state-changing path runs inside one Spring transaction.

## 9. Duplicate Semantics

### New identity

No row exists:

```text
INSERT PROCESSING
execute adapter
persist events
UPDATE COMPLETED
return new result
```

### Completed duplicate, same request

Existing row:

```text
state = COMPLETED
tool_name matches
request_digest matches
```

Behavior:

- do not call adapter
- do not append duplicate Tool execution events
- reconstruct previous `ToolExecutionResult`
- return existing request/response/state evidence references

### Same identity, different request

If either differs:

```text
tool_name
request_digest
```

throw:

```text
BusinessException(ErrorCode.IDEMPOTENCY_CONFLICT)
```

No adapter call and no mutation.

### Existing PROCESSING row

Return:

```text
BusinessException(ErrorCode.IDEMPOTENCY_IN_PROGRESS)
```

This is retryable according to the existing ErrorCode contract.

## 10. Transaction Boundary

For a new state-changing Tool call, the following must share one transaction:

```text
idempotency reservation
TOOL_REQUEST event
adapter DB mutation
TOOL_RESPONSE event
SANDBOX_STATE_CHANGED event if any
idempotency COMPLETED transition
```

Failure before transaction commit:

```text
all changes rollback
```

Failure after commit but before caller receives the response:

```text
retry finds COMPLETED receipt
adapter is not executed again
previous result is returned
```

This provides the required exactly-once mutation boundary for sandbox state.

## 11. Evidence Correlation

Tool-related execution events for a state-changing invocation should include:

```text
toolCallId
```

in metadata.

Required correlation:

- `TOOL_PROPOSED.eventId == toolCallId`
- `TOOL_REQUEST.metadata.toolCallId == toolCallId`
- `TOOL_RESPONSE.metadata.toolCallId == toolCallId`
- `SANDBOX_STATE_CHANGED.metadata.toolCallId == toolCallId`
- existing `sourceToolResponseEventId` remains present for state-change causality.

This supplements rather than replaces existing event-chain integrity.

## 12. Security and Integrity Rules

Fail closed when:

- `toolCallId` is null.
- `requestDigest` is null/invalid.
- `toolCallId` does not resolve to a `TOOL_PROPOSED` event.
- proposal event belongs to another run/caseRun.
- proposal event tool name differs.
- stored digest differs from incoming digest.
- completed receipt references missing response evidence.
- `stateChanged=true` but state event is missing.
- namespace/case-run provenance is invalid.

The AI must never submit namespace, caseRunId, human approval, or toolCallId through Tool args.

## 13. Adapter Changes

### LoanDecisionUpdateMockToolAdapter

Declare:

```text
STATE_CHANGING
```

Keep existing mutation logic and argument/context validation.

Do not embed idempotency SQL inside this adapter.

### ExternalHttpMockToolAdapter

Declare:

```text
STATE_CHANGING
```

The mock collector row creation must be protected by the same common idempotency service.

No real HTTP/network behavior is introduced.

### Read-only adapters

Remain `READ_ONLY` by default.

No idempotency receipt is created.

## 14. Compatibility

The design intentionally preserves:

- `ToolProposal` shape
- `SandboxExecutionContext` shape
- Oracle contracts
- FA-05 trusted before/after snapshot logic
- completed TestRun replay behavior
- Policy decision semantics
- no-real-network invariant
- existing V1-V12 migrations

Expected signature changes are limited to the invocation propagation path:

```text
AgentRuntimeService
AgentToolLoopService
ToolDispatcher
PolicyGateway
TemporaryPolicyGatewayBridge
```

## 15. TDD Implementation Sequence

### Task 8-1: Canonical invocation identity

RED:

- first Tool proposal uses its own `TOOL_PROPOSED.eventId` as toolCallId.
- follow-up proposals each receive their own stable toolCallId.
- requestDigest equals the persisted proposal event payload digest.

GREEN:

- introduce `ToolInvocation`.
- propagate it through ToolLoop -> Dispatcher -> Gateway.
- no DB migration yet.

### Task 8-2: V13 + sequential duplicate protection

RED:

- same caseRunId + same toolCallId + same digest is invoked twice.
- `LOAN_DECISION_UPDATE` changes version exactly once.
- second call returns same response evidence/result.

GREEN:

- V13 migration.
- StateChangingToolExecutionService.
- adapter effect classification.
- common gateway integration.

### Task 8-3: Payload conflict

RED:

- same `(caseRunId, toolCallId)` with different request digest.

Expected:

```text
IDEMPOTENCY_CONFLICT
```

No second mutation.

### Task 8-4: Concurrent duplicate

RED:

- two concurrent invocations with same identity.

Expected:

- one mutation commit
- one final COMPLETED receipt
- duplicate path never produces a second mutation

A transient concurrent caller may receive `IDEMPOTENCY_IN_PROGRESS`, then retry to get the completed result.

### Task 8-5: Regression

Verify:

- FA-03 EXTERNAL_HTTP golden flow
- FA-04 EXTERNAL_HTTP golden flow
- FA-05 mutation golden flow
- FA-05 completed replay
- all current adapter contract/safety tests
- full Gradle suite

## 16. Explicit Non-Goals

Not part of this change:

- SEAL human-only policy implementation
- real HTTP calls
- provider-originated tool IDs
- distributed cache for idempotency
- cross-TestRun Tool replay
- changing API-level idempotency tables
- rewriting V1-V12
- modifying Oracle ownership boundaries

## 17. Acceptance Criteria

The implementation is complete only when all are true:

1. Every state-changing adapter declares `STATE_CHANGING`.
2. Every state-changing invocation has a Spring-owned `toolCallId`.
3. `(test_case_run_id, tool_call_id)` is DB-unique.
4. Same identity + same digest executes mutation once.
5. Same identity + different digest fails with `IDEMPOTENCY_CONFLICT`.
6. Concurrent duplicate cannot commit two mutations.
7. Completed duplicate returns persisted result without new Tool execution evidence.
8. Event metadata preserves `toolCallId` correlation.
9. FA-04 and FA-05 golden flows remain green.
10. Existing V1-V12 files are byte-for-byte untouched.
